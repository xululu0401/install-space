# 安装腾挪台

游戏和软件越来越大，腾出最终安装体积，却可能卡在更新中途：旧版本还没移除，下载包、新版本和临时文件已经同时占着空间。安装腾挪台把这件事拆成可复算的阶段账。

【怎么用】
填同一磁盘的初始空闲和希望保留的空间，再逐行输入任务名称、旧版本、新版本、下载包、临时空间。统一用GiB，最多12项独立更新，每个容量最多两位小数。页面即时比较原顺序和最优顺序，并列出每步开始前、执行中最低、完成后的空闲。

【一组已验算的假设】
默认初始空闲60 GiB、保留10 GiB。设计软件旧10新30、包10临时5；素材工具旧20新25、包10临时0；旧游戏旧40新10、包5临时5。
原顺序需要65.00 GiB初始空闲，当前缺5.00 GiB。改为旧游戏→素材工具→设计软件，需要30.00 GiB，峰值需求降低35.00 GiB。两种顺序全部完成后的空闲都为65.00 GiB。顺序改变中途峰值，不创造磁盘容量。这是教学假设，不是某款游戏安装器实测。

【计算依据】
单项额外需求=新版本+下载包+临时空间；完成后的占用变化=新版本−旧版本。用子集动态规划比较所有任务排列的最大占用，求这组假设下的最小峰值，并加上保留空间。没有主观权重或设备评分。多种顺序可能并列最优。

【能带走什么】
一键采用推荐顺序；把空闲改成刚好够用的数值进行试算；条件自动保存在本机，可备份JSON并恢复。CSV和Markdown导出全部两种顺序的明细，PNG导出摘要（最多展示前8项）。所有计算在浏览器本地执行，不扫描、不读取、不删除磁盘文件。

【边界】
任务必须独立、单卷、串行；假设旧版与全部新文件同时共存，完成后才清理旧版、下载包与临时文件。不支持跨盘、依赖、共享缓存、增量补丁、压缩/稀疏文件或后台写入；实际安装器可能复用或保留文件。0.01 GiB是输入刻度，不是逐字节检测。负的空闲只是不可执行情景的算术结果。保留空间由使用者决定，不是系统标准，也不保证安装成功。

【版本与验证】
v1.0.0。核心测试含300组独立全排列空间模拟；实际浏览器检查条件修改、空间不足、异常拦截、保存刷新、备份往返、四种下载和手机布局。说明里的数字由同一套已验算结果导出。
